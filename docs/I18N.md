# Internationalization (I18N)

## Overview

This document explains how internationalization is implemented inside Open Library Front.

The project supports multiple languages through a dedicated localization layer built with i18next.

Internationalization is treated as an architectural concern rather than a UI-only feature.

The goal is to provide:

- localized interface text
- language-aware content resolution
- predictable language switching
- maintainable translation ownership
- scalable multilingual support

---

## Philosophy

The project separates localization into two independent concerns:

- UI translation
- data localization

These concerns behave differently and are intentionally handled separately.

UI translation controls static interface text.

Data localization controls how external content is resolved and presented.

This separation avoids coupling rendering behavior with translation state.

---

## Technology Choice

Internationalization is implemented using:

- i18next
- react-i18next
- i18next-browser-languagedetector

This stack was chosen because it provides:

- mature ecosystem
- React integration
- scalable namespace support
- language detection
- predictable runtime behavior

---

## Supported Languages

The current implementation supports:

- English
- Portuguese
- Spanish

Language resources are organized through translation dictionaries.

Example structure:

```txt
shared/i18n
├── locales
│   ├── en
│   ├── pt
│   └── es
```

This organization keeps translations isolated and scalable.

---

## Translation Ownership

UI translations live inside dedicated locale files.

Example:

```txt
locales/en
```

These files own:

- labels
- buttons
- messages
- empty states
- validation text
- UI copy

Components do not own translated strings directly.

Instead, components request translations through i18next.

Example:

```tsx
t('books.search.placeholder');
```

This avoids:

- hardcoded copy
- duplicated text
- inconsistent wording
- difficult maintenance

---

## Language Detection

The project uses browser language detection.

Detection is handled through:

```txt
i18next-browser-languagedetector
```

Typical sources include:

- browser language
- navigator preferences
- persisted language settings

This improves first-load experience by reducing manual setup.

Users receive a localized experience automatically.

---

## Fallback Strategy

The application uses fallback language behavior.

If a translation key or language resource is unavailable, the system falls back to a stable language configuration.

This prevents:

- broken UI copy
- missing labels
- runtime translation failures

Fallback behavior is treated as part of resilience strategy.

Internationalization should fail gracefully.

---

## Translation Structure

Translations are grouped using semantic namespaces and structured keys.

Example:

```txt
books.search.placeholder
```

The project avoids flat translation structures.

Benefits include:

- better organization
- easier scaling
- clearer ownership
- reduced naming collisions

This becomes increasingly important as applications grow.

---

## Locale and Data Resolution

Internationalization in Open Library Front extends beyond UI labels.

Language also influences content resolution.

Book entities may contain:

- localized titles
- language-specific metadata
- alternative representations

The project resolves these variations through dedicated normalization and resolver logic.

Example:

```txt
resolveBookLocale()
```

This keeps localization behavior explicit and predictable.

---

## Why Locale Resolution Exists

A naive implementation could mutate already-rendered entities when language changes.

Example issues:

- title switching during render
- cover instability
- flickering UI
- inconsistent entity state

The project avoids this.

Instead, language-aware values are resolved before rendering.

This produces:

- stable UI
- predictable rendering
- cleaner components
- reduced runtime mutation

Locale behavior becomes a data concern rather than a rendering side effect.

---

## Language Switching

Language switching is intentionally centralized.

The i18n layer owns:

- active locale
- translation resource selection
- rerender propagation

UI components do not manually coordinate localization behavior.

This prevents:

- duplicated logic
- inconsistent updates
- fragmented language state

Language becomes a shared application concern.

---

## UI Localization Principles

The project follows several localization principles.

### No Hardcoded User Copy

User-facing text should not live inside components.

Instead:

- translations belong to locale files
- components request translated values

This improves maintainability.

---

### Translation Keys Over Raw Strings

The project prefers semantic translation keys.

Example:

Preferred:

```txt
books.empty.title
```

Avoid:

```txt
"No books found"
```

Semantic keys improve:

- readability
- reuse
- translation management

---

### Stable Translation Ownership

Each translation should have a clear ownership location.

This avoids:

- duplicated copy
- conflicting wording
- scattered translations

Ownership remains centralized.

---

## Accessibility and Localization

Internationalization also supports accessibility goals.

Localized UI improves:

- readability
- navigation clarity
- comprehension
- user confidence

Accessible interfaces are not only semantic.

They must also be understandable.

Localization contributes directly to this experience.

---

## Tradeoffs

The current i18n architecture intentionally favors explicit organization.

Benefits:

- scalable localization
- predictable language behavior
- cleaner components
- maintainable translations

Tradeoffs include:

- additional setup
- translation maintenance overhead
- larger resource management needs

These tradeoffs were considered acceptable for long-term maintainability.
